# 전북대 학교·학과 공지 수집 설계

> 확인 기준일: 2026-08-24
> 범위: 로컬에서 실행하는 수강길잡이 V2

## 1. 결론

공식 API나 RSS가 없다면 **공개 HTML을 낮은 빈도로 서버 측에서 수집하는 방식**이 적합하다. 다만 사용자가
공지 화면을 열 때마다 학교 사이트를 실시간 크롤링하면 안 된다. 수집 장애와 응답 지연이 화면으로 전파되고 같은
문서를 반복 요청하며, 수정 공지와 키워드 알림의 기준 시점을 관리하기 어렵기 때문이다.

```text
전북대 공개 공지 -> 로컬 수집 명령 -> 정규화 DB -> 공지 화면·인앱 알림
```

우선순위는 다음과 같다.

1. 공식 API, RSS, 공개 JSON/XHR, 공식 파일 제공 여부를 먼저 확인한다.
2. 제공 수단이 없고 공개 열람이 허용된 경우 `fetch`와 HTML 파서로 수집한다.
3. JavaScript 실행 없이는 내용을 얻을 수 없는 출처에만 브라우저 자동화를 검토한다.
4. 로그인, CAPTCHA, 접근 제한을 우회해야 하는 출처는 수집하지 않는다.

## 2. 확인한 전북대 공지 구조

| 구분 | 확인한 공식 페이지 | 구조 | 권장 어댑터 |
| --- | --- | --- | --- |
| 학교 본부 교내공지 | [전북대 교내공지](https://www.jbnu.ac.kr/mobile/notice/sub01.do) | 공개 서버 렌더링 HTML, 분류·제목·작성자·게시일 제공 | `jbnu-main` |
| 학교 본부 학생공지 | [전북대 학생공지](https://www.jbnu.ac.kr/web/news/notice/sub02.do) | 별도의 공개 학교 공지 채널 | `jbnu-main` |
| 컴퓨터인공지능학부 일반공지 | [학부 공지](https://cs.jbnu.ac.kr/csai/29106/subview.do) | K2Web 공개 HTML, 외부 게시물 ID와 목록·상세 URL 제공 | `k2web` |
| 컴퓨터인공지능학부 학사공지 | [K2Web 목록](https://cs.jbnu.ac.kr/bbs/csai/4929/artclList.do) | K2Web 공개 HTML, 게시판 ID가 일반공지와 다름 | `k2web` |

- 학교 본부는 용량이 작은 모바일 목록을 수집하고 사용자에게는 공식 웹 상세 링크를 제공하는 편이 효율적이다.
- 학교 대표 사이트의 `robots.txt`는 전체 경로의 수집을 허용하고 있다.
- 확인한 컴퓨터인공지능학부 호스트에는 `robots.txt`가 없었다. 파일이 없다는 사실은 재사용 허가를 뜻하지 않는다.
- 조사한 페이지는 JavaScript 실행 없이 목록과 상세 내용을 읽을 수 있으므로 Playwright는 필요하지 않다.
- K2Web을 쓰는 학과끼리는 파서를 공유할 수 있지만 사이트 ID와 게시판 ID가 다르다. 모든 학과가 K2Web이라고
  가정하지 말고 출처별 fixture 테스트를 둔다.

## 3. 사용자별 노출 규칙

### 3.1 학교 본부 공지

- `scope = UNIVERSITY`로 한 번만 저장한다.
- `/notices`를 공개 경로로 두고 로그인 여부와 무관하게 최근 학교 공지를 보여준다.
- 사용자별로 같은 공지를 복제해 저장하지 않는다.

### 3.2 학과 공지

- `scope = DEPARTMENT`와 표준 `departmentKey`를 함께 저장한다.
- 로그인한 사용자의 학과 키는 서버 세션과 사용자 레코드에서 읽는다.
- 클라이언트가 보낸 `department` 검색 파라미터를 접근 조건으로 신뢰하지 않는다.

```sql
scope = 'UNIVERSITY'
OR (
  scope = 'DEPARTMENT'
  AND department_key = current_user.department_key
)
```

현재 프로그램의 `users.department`는 가입 화면에서 선택하지만 서버에서는 비어 있지 않은지만 검사하며, 과목
데이터의 학과명을 그대로 선택지로 사용한다. 학과 공지를 연결하기 전에 다음처럼 표준화해야 한다.

```text
사용자 저장값/별칭 -> 표준 departmentKey -> 허용된 notice source
```

예를 들어 `컴퓨터인공지능학부`, 이전 학과명, 전공 표기를 하나의 표준 키로 연결하고, URL은
`department_source_map`에 등록한 값만 사용한다. 연결되지 않은 학과는 학교 본부 공지만 보여주고
`아직 연결되지 않은 학과`라고 표시한다.

## 4. 데이터 모델

| 테이블 | 핵심 필드 |
| --- | --- |
| `notice_sources` | 이름, `UNIVERSITY/DEPARTMENT`, 원본 URL, 어댑터 키, 허용 상태, 마지막 성공·실패 시각 |
| `department_source_map` | 표준 학과 키, 출처 ID, 학과 별칭, 활성 상태 |
| `notices` | 출처 ID, 외부 게시물 ID, 제목, 짧은 본문 텍스트, 게시·수정일, 원문 URL, 상태, 마지막 확인 시각 |
| `notice_versions` | 공지 ID, 내용 해시, 변경 필드, 확인 시각 |
| `notice_attachments` | 공지 버전, 파일명, 공식 원문 URL, 크기·형식 메타데이터 |
| `keyword_subscriptions` | 사용자, 키워드·동의어, 적용 출처, 활성 상태 |
| `notice_matches` | 공지 버전, 구독 ID, 일치 문구, 읽음 상태 |

- 공지 고유 제약은 `(source_id, external_id)`로 둔다.
- 내용 해시는 정규화된 제목·본문·첨부 이름과 URL·중요 날짜로 만든다.
- 조회수와 수집 시각은 내용 해시에서 제외한다.
- 중앙 공지를 학과가 재게시한 경우 하나를 삭제하지 않고 동일 문서 후보로 그룹화해 출처 배지를 함께 보여준다.

## 5. 로컬 수집 흐름

기본 실행 명령은 `pnpm notices:sync`로 한다. 앱과 PC가 꺼져 있을 때는 공지를 수집하거나 알림을 만들 수 없다.
시연 중 자동 갱신이 필요할 때만 Windows 작업 스케줄러로 3~6시간마다 같은 명령을 실행한다.

1. 활성 출처와 허용 상태를 읽는다.
2. 호스트별 동시 요청을 1개로 제한하고 목록의 최근 20~50건을 가져온다.
3. 목록 URL에서 외부 게시물 ID를 추출한다.
4. 신규 항목이나 목록 메타데이터가 바뀐 항목만 상세 페이지를 요청한다.
5. HTML을 직접 저장·렌더링하지 않고 허용한 텍스트와 메타데이터만 정규화한다.
6. 내용 해시가 같으면 `lastSeenAt`만 갱신하고, 다르면 버전을 추가한 뒤 수정 알림 후보를 만든다.
7. 키워드를 정규화한 제목·본문과 비교하고 일치 문구가 있는 경우에만 인앱 알림을 만든다.
8. 수집 결과와 마지막 성공·실패 시각을 기록한다.

응답이 `ETag` 또는 `Last-Modified`를 제공하면 조건부 GET을 사용한다. `429`의 `Retry-After`를 지키고,
timeout과 지수 백오프를 적용한다. 목록에서 한 번 보이지 않은 공지는 삭제하지 않으며 상세 `404` 또는 2~3회
연속 미확인을 확인한 뒤 삭제 상태로 바꾼다. 파싱 건수가 갑자기 줄거나 필수 필드가 사라지면 기존 데이터를
건드리지 않고 출처 오류로 처리한다.

## 6. 코드 배치 제안

```text
lib/notices/adapters/jbnu-main.ts
lib/notices/adapters/k2web.ts
lib/notices/normalize.ts
lib/notices/sync.ts
lib/notices/queries.ts
lib/db/scripts/sync-notices.ts
app/notices/page.tsx
```

K2Web 어댑터에는 `origin`, `siteId`, `boardId`, `listUrl`만 설정으로 전달한다. 학과명을 URL에 삽입하지 않고
DB에 허용 목록으로 등록한 출처만 호출한다. 각 어댑터는 저장해 둔 목록·상세 HTML fixture로 파서 테스트를 한다.

## 7. 개인정보·저작권·보안

- `robots.txt` 허용과 콘텐츠 재사용 허가는 별개로 기록한다. 전북대 [홈페이지운영지침](https://www.jbnu.ac.kr/web/info/09.do)은
  홈페이지에서 얻은 정보를 관리자 사전 승낙 없이 복제하거나 제3자에게 제공하는 행위를 사용 제한 사유로
  명시한다. 출처별 이용 조건과 담당 부서 확인 상태를 `허용`, `확인 중`, `사용 불가`로 관리한다.
- 원문 전체를 서비스가 대신 제공하지 않고 제목, 날짜, 출처, 짧은 문맥과 공식 원문 링크 중심으로 표시한다.
- 학교 HTML을 그대로 렌더링하지 않고 텍스트로 정규화해 스크립트와 위험한 마크업을 제거한다.
- 이동 링크와 첨부 링크는 검증한 `https://*.jbnu.ac.kr` 호스트만 허용하고 리디렉션 목적지도 검사한다.
- 첨부에는 학번, 연락처, 지원자 명단이 있을 수 있다. MVP에서는 파일을 다운로드·전문 색인·AI 전송하지 않고
  파일명과 원문 링크만 제공한다.
- `403`, `429`, CAPTCHA, 로그인이 나타나면 우회하지 않고 해당 출처를 중지한다.

## 8. 구현 순서

1. 학교 본부 공지 한 곳과 컴퓨터인공지능학부 공지 한 곳만 연결해 파서와 데이터 모델을 검증한다.
2. 표준 학과 원장과 학과별 출처 매핑을 만들고 회원가입·사용자 학과 데이터를 마이그레이션한다.
3. 공개 `/notices`의 `전체 공지`와 로그인 전용 `내 학과 공지` 조회를 구현한다.
4. 멱등 동기화, 수정 감지, 수집 실패 상태, 타 학과 접근 차단 테스트를 추가한다.
5. 단순 키워드·동의어 매칭과 인앱 알림을 추가한다.
6. 학과별 출처를 한 곳씩 확인하며 확장한다. 이후 이용 허용이 확인된 첨부 형식과 AI 요약을 별도 단계로 검토한다.

현재 Next.js·Drizzle 구조와 `users.department`는 이 기능을 담을 수 있다. 다만 공지 기능 자체는 아직 없으며,
정확한 학과 분리를 위해 **표준 학과 키와 출처 허용 목록을 먼저 만드는 작업이 필수**다.
