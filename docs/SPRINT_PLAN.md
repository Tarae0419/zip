## 문서 관리 방법

- 작업을 끝낼 때마다 해당 체크박스를 `- [ ]` → `- [x]`로 바꾼다. 완료 조건(DoD)을 모두 만족했을 때만 체크한다 — 코드가 있다고 체크하지 말고, 각 항목 하단의 **DoD**를 실제로 충족했는지 확인한다.
- 스프린트를 통째로 끝내면 위 표의 **상태** 줄과 아래 **진행 현황 요약**의 상태 컬럼을 함께 갱신하고, **최종 수정일**을 갱신한다.
- 스프린트는 순서대로 진행하는 것을 기본으로 한다. 앞 스프린트의 선행조건이 끝나지 않았는데 뒤 스프린트를 먼저 시작해야 하면, 그 사실과 이유를 해당 스프린트의 "메모" 항목에 남긴다.
- 진행 중 PRD에 없던 결정(예: 데이터 소스 변경, 범위 축소)을 내리면 하단 **오픈 이슈 / 의사결정 로그**에 날짜와 함께 기록한다. PRD 자체는 별도 합의 없이 고치지 않는다.
- 새 작업이 필요해지면 해당 스프린트 안에 항목을 추가하고, 기존 번호 체계를 건드리지 않도록 하위 항목(예: `1.4.1`)으로 끼워 넣는다.

  - 결정: 최초 5개 도달 시 1차 생성, 이후 유효 리뷰가 3개 늘어날 때마다 재생성(`SUMMARY_REGEN_INCREMENT = 3`, `lib/actions/reviews.ts`). 매 리뷰마다 재생성하면 비용이 계속 나가므로 완충 구간을 뒀다. 리뷰 등록 Server Action 안에서 동기 처리 — 서버리스 요청 하나가 리뷰 저장+AI 호출을 함께 하므로, 향후 리뷰량이 많아지면 비동기/큐로 옮기는 걸 Sprint 7에서 재검토.
- [x] 2.5 극단적 리뷰 처리 — 평점이 크게 갈리는 과목은 요약에 "호불호가 갈리는 강의"를 명시하도록 프롬프트 반영 (PRD 8.1 Edge Case)
  - DoD: 의도적으로 평점이 양극화된 테스트 데이터로 생성했을 때 요약 문구에 반영됨을 확인한다.
  - 구현: 4~5점과 1~2점 비율이 전체의 60% 이상이면 `isPolarized`로 판단해 프롬프트에 지시 추가. 평점 5·2·4·5·1로 구성된 테스트 데이터로 실제 생성해 "호불호가 갈리는 평판"이라는 문구가 요약에 포함됨을 확인.

**메모(다음 세션에서 브라우저로 직접 확인할 것)**: "AI로 태그 추천받기" 버튼 클릭, AI 요약 카드가 실제 화면에 표시되는 모습은 이번에도 curl/직접 스크립트로만 검증했고 브라우저 클릭으로는 못 봤다(브라우저 자동화 도구 없음). 로직 자체는 실 OpenAI API + 실 DB로 검증 완료.
